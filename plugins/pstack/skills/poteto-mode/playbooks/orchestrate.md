### Orchestrate

**You run the program, never the code. Decide which agent does each piece of work, then check what each one produces.** For a standing project handed to one coordinator chat: multi-day, many stacked PRs, dozens to hundreds of subagents, few human turns. One task driven to a predicate is Autonomous run. One ambitious run that needs a bespoke workflow is figure-it-out. Work that one agent could finish inside the session's budget is not a program.

Run it with your own tools. Spawn workers through [provider dispatch](../references/provider-dispatch.md): the `Agent` tool or Codex's `spawn_agent` for a native lane, and the launcher for an external one. Keep the program's state in `<config-home>/orchestrate/<project-slug>/notes.md`, with `<config-home>` resolved as [Harness config homes](../references/codex-tools.md#harness-config-homes) says: the goal, the standing constraints, and each unit's owner, branch, PR, and verdict head. Keep kickoffs and reports in the same directory. The program outlives this session and the todolist does not, so that directory is the record. Every file there has one writer, and the coordinator is the writer of `notes.md`. Run no bookkeeping scripts and no polling loops of your own, and never relay messages or status between agents.

Each owner waits on its own PR through `playbooks/babysit.md`, and its completion notice wakes you: a background task notification on Claude Code, or `wait_agent` on Codex. Claude Code and Codex give the coordinator no PR or CI event subscription of their own. In T3 Code, use the watcher in Babysit step 6 in place of the owner's script, when the thread that owns the PR has it. An agent that never reports sends no notice, so arm the audit tick in `playbooks/autopilot-full.md` step 6 on the operator's go. That tick observes. It is never a lease or a deadline.

#### Topology

- **One owner per PR.** The owner is the only writer of its branch and carries the PR from build to merge. Only the owner pushes, rebases, or retargets it, through the disarm and captured-SHA lease steps in `playbooks/autopilot-full.md` step 2. Closing or retargeting a base PR orphans every PR above it, so the owner does that only on your call. You never author or edit code. Conflicted merges, chain rebases, and fixes go to owners.
- **A fresh worker for each independent task.** Its kickoff carries everything it needs, including each upstream report it depends on, pasted in full. Workers can't see their siblings. Every worker is a background subagent or a background launcher process on this machine, so isolate each writer in its own worktree or branch (principle-separate-before-serializing-shared-state). Runtime checks go through the `run` skill (CLIs and TUIs) or the `verify` skill (UIs). Pick each subagent's effort for the job, per the Subagents section.
- **A sub-coordinator only when one area has many parallel workers, and only where the runtime lets a subagent spawn one.** It owns that area's workers and kickoffs and sends you one rollup, never raw worker reports. Where a subagent cannot spawn, stay flat and run the area's workers yourself. Stop at three levels: you, sub-coordinators, and workers. Keep about ten workers in flight per coordinator, and start the next one as each finishes instead of waiting on a whole batch.
- **Reuse a worker only when new work needs its built state,** such as its checkout, uncommitted changes, or a running process. Otherwise follow poteto-mode's Fresh subagents rule. Message a worker only for a follow-up on the same work. Never message one to check on it, because a message restarts an idle agent.
- **Each PR gets a verifier that isn't its author,** on a different model family, routed through provider dispatch. The owner merges only on that verifier's pass at the current head, and only through the expected-head flow in `playbooks/shipping.md` step 5.
- **Start with one unit.** Take it through kickoff, owner, verifier, and merge before you fan out, so a flaw in the kickoff costs one agent instead of fifty. On near-identical cheap units, the first unit is that test.

#### Supervision

- **Each kickoff names the evidence that proves the work is done,** such as a command and its expected output, a `run` or `verify` check, or an artifact. It also names the goal, the paths the worker may and may not write, and the actions it must not take. If you can't name the evidence, the unit isn't scoped yet.
- **Read the diff or the artifact, not only the worker's summary.** Green CI is an input to a verdict, not a verdict. Behavioral work needs more than a type check. A verdict covers one head SHA, so a new push needs a new verdict, except for results that stay valid under the patch ID rule in `playbooks/shipping.md`. Read a sample of each sub-coordinator's kickoffs while its workers run, and fix its instructions when one fails.
- **Send back work that drifts from scope or grows past what was asked.** Keep only the fixes that block the program, and park the rest as follow-ups.
- **Check a PR's live state before you report on it,** with `gh pr view "$pr" --repo "$base_repo"` and `gh pr checks "$pr" --repo "$base_repo"`, or Origin's equivalents when Origin is the resolved forge, not the worker's last report. Account for every worker you spawned as done, replaced, or absorbed into another worker's scope.
- **Stop or replace a worker only on affirmative failure evidence,** as `playbooks/autopilot-full.md` step 6 says: it errors, its process is dead, its handle fails, it cannot start turns, it loops on the same failed action, or a caller-supplied external deadline passed. Judge it by its pushes and PR activity, not its status text, but elapsed time or no new activity alone is drift to record, not a stall. Retry by cause: a smaller scope after a context or memory limit, the same kickoff after a dropped connection, and another configured role's model after a tool error, named in your report. An unavailable model stays a named dropout. After two retries, drop the unit and replan around it. When a stopped worker returns late, check its result against the PR's current state, and hand any unique findings to a fresh worker.
- **After a session restart, reattach by PR and branch.** In-flight subagents are dead. Pushed branches, open PRs, and the program's directory are not. Re-read `notes.md`, check each PR's live state, and start a fresh worker for what was in flight.
- **Ask the user only for a real decision or a blocker,** such as an irreversible action, a product or preference call that no experiment settles, or a dead end that survived a replan. Rebase mechanics, retries, CI flakes, review triage, and "should I keep going" never reach the user.

**Reply:** what landed against the goal, each PR's live state and verdict with its link, what was dropped and why, and the decisions waiting on the user.
