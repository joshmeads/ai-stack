### Autopilot-stack

**Autopilot-full without the merge. You own each stack's topology, never the landing. Hand the operator verified PRs to review and land.** **Autopilot-full** holds except for how verified work leaves. Each tick re-reads both playbooks from disk (`skills/poteto-mode/playbooks/autopilot-stack.md` and `autopilot-full.md` under the installed plugin), and this one wins where they differ. Every loop tick prompt names this file, so each tick sees the no-merge rule.

1. **Run Autopilot-full's owners. In place of its step 5, stop at verified.** Resolve the forge, `<base-repo>`, `<head-remote>`, `<head-url>`, and `<base-remote>` as Autopilot-full step 2 does; this playbook never merges. When the head repository is a fork, validate its identity and record its owner and repository name as `<fork-owner>` and `<head-name>`. Stop when each PR is verified and green at its current head, then hand the PRs to the operator. After the handoff, nobody pushes without the operator's go. Owners report merge-ready with the exact head SHA. No owner retargets, merges, or closes a PR, or arms auto-merge, because the root owns each chain's topology and the operator owns the landing. The owner of a stack link never rebases onto another branch, trunk included. When an item depends on another, its owner branches from that item's branch, not from trunk. Nothing enters a stack before a clean verdict from Autopilot-full step 4.
2. **Stack a PR only when it builds on another PR, and give each stack's topology one writer.** This is the one exception to Autopilot-full step 3. An independent PR stays off trunk, and its owner rebases it as Autopilot-full step 2 says. In a stack, owners push only their own branches and report each tip, its current patch base, and its intended parent. Only you rebase or retarget a link, because two writers on one chain undo each other. Append each clean PR to one frozen bottom-to-top list in dependency order, or an order the operator specified. For same-repository heads, the forge's base-branch chain also records that order. For fork heads, every PR targets trunk, so never infer stack order from their equal base branches. Never require Graphite (`gt`). An owner takes your push as its new base and lease, and on a conflict resolves its own slice for you to push.

   Before you rebase, force-push, or retarget an existing PR, apply Shipping step 4's disarm-and-confirm rule to that PR and every descendant, stopping if the forge cannot confirm every request off. Fetch trunk through `<base-remote>`. Fetch another stack branch directly through `<head-url>`, because `<head-remote>` may have the base repository as its fetch URL and the fork as its push URL. Validate the chosen repository identity through the active forge, and record the fetched target as `<parent-tip>`. Before rebasing, record the child branch's published SHA as `<captured-sha>` with `git ls-remote -- "$head_url" "refs/heads/$branch"` and require it to equal the local pre-rebase tip. Require `git merge-base --is-ancestor "$current_base_sha" "refs/heads/$branch"` to pass. When the parent changed, move only the child's commits with `git rebase --onto "$parent_tip" "$current_base_sha" -- "$branch"`, then record `<parent-tip>` as the child's new patch base. Publish with `git push --force-with-lease="refs/heads/$branch:$captured_sha" -- "$head_url" "HEAD:refs/heads/$branch"`. When the head and base repositories are the same, create or retarget the child PR with the parent branch as its base. Use `origin pr create --status open --base "$parent_branch"`, `gh pr create --base "$parent_branch" --repo "$base_repo"`, `origin pr edit "$pr" --base "$parent_branch"`, or `gh pr edit "$pr" --base "$parent_branch" --repo "$base_repo"` according to the resolved forge and operation. When the head repository is a fork, keep the local child branch rebased onto its parent's exact tip but create or retarget every PR against `<trunk>` in the base repository. With GitHub, capture the approved PR title and body as `<title>` and `<body>`, then create it with `gh api --method POST "repos/$base_repo/pulls" -f "title=$title" -f "body=$body" -f "head=$fork_owner:$branch" -f "head_repo=$head_name" -f "base=$trunk" --jq .html_url`; add `-F draft=true` only when Opening a PR's readiness rule requires a draft. Otherwise use the resolved Origin equivalent. Retarget it with `gh pr edit "$pr" --base "$trunk" --repo "$base_repo"` or the resolved Origin equivalent. A forge cannot use a fork-only parent branch as a PR base.
3. **Absorb drift at the root.** Until landing starts, fetch current trunk through `<base-remote>` and rebase the chain bottom-up with step 2's explicit old-base and new-parent flow. A new head on a lower link restacks the links above it. When a rebase surfaces conflicts in an owner's files, that owner fixes its own slice and you push the result using step 2's captured-SHA lease flow. A rebase rewrites every SHA above it, so apply the patch-id rule in `playbooks/shipping.md` step 3 link by link, since a link's base is its parent, using each PR's recorded patch-base-to-head diff. Anything no longer valid goes back through Autopilot-full step 4 before delivery. Re-run mergeability and CI after every rewritten push even when the patch ID is unchanged.
4. **Deliver the PRs, then keep your hands off them.** The deliverable is each independent PR and each stack's frozen bottom-to-top list, reviewable in the resolved forge, and each PR carries its verdict. In a stack, same-repository heads use a base-branch chain. Fork heads retain local parent ancestry while every PR targets trunk. The operator sends only the current bottom PR through Shipping, one at a time. A merge-when-ready request applies only to that bottom after Shipping has disarmed and confirmed every descendant; never offer or arm merge-when-ready for the chain as a whole or for a descendant. Once landing starts, nobody writes to the chain except the post-merge move that Shipping step 4 sanctions, because a second writer breaks a landing in flight. A mid-landing problem goes through you to the operator, and any fix waits for the operator's go.
